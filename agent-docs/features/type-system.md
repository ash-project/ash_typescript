# Type System and Type Inference

Core type inference system architecture and schema-based classification for AshTypescript development.

## Schema Key-Based Classification

**Core Insight**: Use schema keys as authoritative classifiers instead of structural guessing.

The TypeScript utility types are generated by `AshTypescript.Codegen.UtilityTypes.generate_utility_types/0` (`lib/ash_typescript/codegen/utility_types.ex`) and emitted into `ash_types.ts` via `SharedTypesGenerator` (`lib/ash_typescript/codegen/shared_types_generator.ex`). Key types include:

- **`UnionToIntersection<U>`** - Converts union types to intersection types for field selection merging
- **`InferFieldValue<T, Field>`** - Infers the result type for a single field selection
- **`InferResult<T, SelectedFields>`** - Infers the final result type for complete field selections
- **`UnifiedFieldSelection<T>`** - Defines valid field selection syntax for a schema
- **`TypedSchema`** - Base constraint: `{ __type: "Resource" | "TypedMap" | "Union"; __primitiveFields: string }`

Also generated there (not listed above): `InferUnionFieldValue`, `InferTypedMapMemberValue`, `SortString`, `ConditionalPaginatedResult`.

These types work together to provide compile-time type safety for field selections, ensuring only valid fields can be selected and the correct result types are inferred.

## Unified Schema Architecture

**Single ResourceSchema per resource** with metadata-driven type inference:

- `__type` metadata for classification
- `__primitiveFields` for TypeScript performance optimization
- Direct field access on schema types
- Utility types: `UnionToIntersection`, `InferFieldValue`, `InferResult`

## Calculation Metadata Pattern

Calculations render as `ComplexCalculation` metadata in the resource schema. The
`__args` key is gated on **argument presence**, not on return type
(`codegen/resource_schemas.ex`, `spec_calculation_definition/2`):

```elixir
# No arguments
"{ __type: \"ComplexCalculation\"; __returnType: #{return_type}; }"

# With arguments
"{ __type: \"ComplexCalculation\"; __returnType: #{return_type}; __args: #{args_type}; }"
```

**0.18 change**: calculations whose manifest type carries a `resource_module`
(i.e. `:struct` + `instance_of: SomeResource`) are classified `:embedded` and
render the relationship wrapper instead — `{ __type: "Relationship"; __resource: X; }`
(or `{ __type: "Relationship"; __array: true; __resource: X; }`). Client field
selection is unchanged; only the `__type` tag differs from pre-0.18 output.

## Field Classification (Manifest-Driven)

Codegen no longer inspects raw `Ash.Resource.Info` structs. Classification runs off
`%Ash.Info.Manifest.Type{}` via `ResourceSchemas.classify_by_type/1`
(`lib/ash_typescript/codegen/resource_schemas.ex`), dispatching on `kind`:

```elixir
:type_ref                      -> resolve via Ash.Info.Manifest.get_type!/2, recurse
:array                         -> recurse into item_type
:union                         -> :union
:resource | :embedded_resource -> :embedded
:map | :keyword | :tuple       -> :typed_map if has_type_fields?, else :primitive
:struct                        -> :embedded      when resource_module
                                  :typed_struct  when instance_of + fields
                                  :typed_map     when fields only
                                  :primitive     otherwise
_                              -> :primitive
```

## Type Mapping Patterns

Kind → TypeScript mapping lives in `@kind_to_ts` / `@primitives` in
`lib/ash_typescript/codegen/type_mapper.ex`.

### Basic Types
- `:string` → `string`
- `:integer` → `number`
- `:boolean` → `boolean`
- `:utc_datetime_usec` → `UtcDateTimeUsec`

Date/time, uuid and decimal kinds route through **named aliases** emitted by
`codegen/type_aliases.ex` (`UtcDateTimeUsec`, `UUID`, `AshDate`, `Decimal`, …),
each of which is `= string` in the generated output — not bare `string`.
Alias collection walks every position the mapper renders inline (array items,
union members, typed map/keyword/struct fields, tuple elements, named-type
definitions), so a type used only nested still gets its alias declared. Roots
are resource fields, calculation arguments, action inputs, returns and
metadata, the `returns` types of the manifest's stored typed channel
publications (their payload types are appended to `ash_types.ts`), and every
aliased definition (declared custom types and aliased field-bearing NewTypes,
`CustomTypeAliases.definitions/0`, so route-only types get their aliases too).

### Complex Types
- Embedded resources → Full resource schema with field selection
- Unions → Union type with selective member fetching
- Scalar custom types → Type name from `typescript_type/0` callback
- Declared (map-like) custom types and aliased field-bearing NewTypes → their
  alias (`Money`, `TaskStats`) at input and plain positions, the inline
  `TypedMap` form at schema positions (see
  [Declared Custom Type Aliases](#declared-custom-type-aliases))

### Third-Party Types

Three dependency types are built-in `custom_types` entries
(`AshTypescript.CustomTypes.Builtin`). Money, a declared custom type, gets the
generated alias every declared type gets; ULID and Ltree get no alias:

| Module | Entry | TypeScript |
|--------|-------|------------|
| `AshMoney.Types.Money` | `map` (`currency`, `amount`) | `export type Money = {currency: string, amount: Decimal};`, referenced at plain positions; a `TypedMap` at schema positions |
| `AshPostgres.Ltree` | `scalar` with MFA `ts_type` | `string[]` when `escape?: true`, else `string \| string[]` |
| `AshDoubleEntry.ULID` | `scalar` over `:string` | `string` |

A manifest entry for the same module replaces the built-in. The Zod/Valibot
schemas come from the same entries (`SchemaCore`, see
[validation-schemas.md](validation-schemas.md)): Money is an object of its
fields (the named `MoneyZodSchema` / `MoneyValibotSchema`), Ltree uses the
built-in's `zod`/`valibot` MFAs, ULID its base type.

## Architecture Benefits

1. **Predictable**: Schema keys provide authoritative classification
2. **Performance**: Direct field access, no nested conditionals
3. **Maintainable**: Single source of truth per resource
4. **Extensible**: Clear extension points for new types

## Custom Types Integration

**See also**: [Field and Argument Name Mapping](./field-argument-name-mapping.md) for mapping invalid field names in custom types using the `typescript_field_names/0` callback.

### TypedStruct and NewType Field Name Mapping

Types implementing `typescript_field_names/0` can map internal field names to TypeScript-compatible names:

```elixir
defmodule MyApp.CustomMetadata do
  use Ash.Type.NewType,
    subtype_of: :map,
    constraints: [fields: [field_1: [type: :string]]]

  def typescript_field_names do
    [field_1: "field1"]  # Values must be strings
  end
end
```

**Note**: The callback returns a keyword list where values are **strings** (not atoms). `RpcMappingSource.type_field_names/1` reads it once, when the manifest is decorated; codegen and the runtime both use the decorated names (codegen through `AshTypescript.Codegen.ClientNames.type_field/2`, so a typed-map return, a `:struct` NewType without `instance_of` and a union member all use them). The callback applies to types only: on a resource it is ignored (use `field_names`).

Typed containers are rendered from their decorated `%Ash.Info.Manifest.Type{}`: `AshTypescript.Codegen.build_map_type/2` takes the container type (plus an optional field selection), and `TypeMapper.build_union_type_from_members/1` / `build_union_input_type_from_members/1` take the union type. A `:type_ref` resolves through `AshTypescript.TypeSystem.Introspection.named_type_definition/1`, which raises for a type missing from the manifest. See [field-argument-name-mapping.md](field-argument-name-mapping.md#where-codegen-gets-names).

### Custom Type Detection

Custom-type detection is consolidated in **one** public function,
`AshTypescript.TypeSystem.Introspection.is_custom_type?/1`
(`lib/ash_typescript/type_system/introspection.ex`). Do not re-implement it locally:

```elixir
def is_custom_type?(type) when is_atom(type) and not is_nil(type) do
  Code.ensure_loaded?(type) and
    function_exported?(type, :typescript_type, 0) and
    Spark.implements_behaviour?(type, Ash.Type)
end

def is_custom_type?(_), do: false
```

Callers: `codegen/type_aliases.ex`, `codegen/type_mapper.ex`, `codegen/schema_core.ex`.

### Type Name Resolution

Custom types provide their TypeScript type name via `typescript_type/0` callback:

```elixir
def typescript_type, do: "CustomTypes.MyType"
```

### Declared Fields (map-like custom types)

A custom type that declares fields becomes a typed map: decoration turns it into a
`:type_ref` to a `kind: :map` definition in `manifest.types`
(`AshRpc.Manifest.Custom.custom_type?/1`), and codegen, selection, input and output
go through the typed-map paths. Fields come from, in order
(`AshTypescript.CustomTypes.fields_for/3`): a `map` entry in the manifest module's
`custom_types` section (one with fields: a field-less entry only opts a field-bearing
NewType into an alias and declares nothing), the type's `typescript_fields/0` (named by
`typescript_field_names/0`), a built-in entry (`AshTypescript.CustomTypes.Builtin`:
`AshMoney.Types.Money`), the subtype's for a NewType, then `composite_types/1`. A
malformed `typescript_fields/0` result is passed on for ash_rpc to reject
(`ArgumentError` naming the module), and so is a field declared twice.
Clients select their fields (`{colorPalette: ["primary", ...]}`); a bare selection is
`requires_field_selection`. A field typed by a module with a `scalar` entry gets the
entry's constraints merged under its own (under `items:` for an array), whichever
source supplies the fields. A `typescript_type/0` or `scalar` entry on such a
type (Money included) is a compile error ("Map-like custom types that declare a
TypeScript type") with a migration message.

```elixir
def typescript_fields do
  [primary: [type: :string, allow_nil?: false], accent: [type: :string]]
end
```

### Declared Custom Type Aliases

Every declared definition (`AshRpc.Manifest.Custom.custom_type?/1`) gets names
at manifest compile: `AshTypescript.CustomTypes.names/2`, written by
`AshTypescript.Manifest.Decorator` under
`custom.ash_typescript.type_alias_names` and read only through
`AshTypescript.Manifest.Custom.type_alias_names/1`
(`%{typescript: name, zod: :derive | nil, valibot: :derive | nil}`). The
TypeScript name (`CustomTypes.alias_name/3`) is the manifest `map` entry's
`ts_alias`, else the type's `typescript_type_alias/0` (also under an entry
without `ts_alias`), else a built-in entry's `ts_alias` (Money:
`"Money"`), else `Codegen.Helpers.module_type_name/1` (the join resources use
too, `SomeLib.Coordinates` → `SomeLibCoordinates`). It is never inherited from
a NewType's subtype. A schema name is `nil` when the effective entry
(`CustomTypes.map_entry/2`, the subtype's for an inheriting NewType) has a
`zod`/`valibot` replacement, else `:derive`: the alias plus the configured
suffix at codegen (`SchemaCore.custom_type_schema_name/2`); there is no
per-type schema name or inline opt-out. `CustomTypes.check_name/2` (used by
`NormalizeCustomTypes` for `ts_alias`, and by `DecorateManifest` through
`CustomTypes.check_alias_names/2` for the callback, which also rejects a
non-string) rejects non-identifiers (anchored with `\A`/`\z`) and
TypeScript/JavaScript reserved words (plus `await`, `eval`, `arguments`); both
are compile errors (`DslError`), not verifier warnings. A type whose callback
names it, and every NewType definition, is a compile dependency of the manifest
(`CustomTypes.compile_dependencies/3`). Names are fixed at decoration:
`with_manifest/2` doesn't change them.

A field-bearing NewType (`CustomTypes.field_bearing_new_type?/1`) that opts in
(a field-less `map` entry, `typescript_type_alias/0`, or `alias_all_types?`)
gets `type_alias_names` too, by the same precedence, beside its `type_name`
when it has one. `CustomTypes.check_alias_names/2` also rejects such a type
when it exports `typescript_type/0`. Codegen reads map-like aliases only
through `CustomTypeAliases.plain_name/1` (any definition with
`type_alias_names`), so an aliased NewType renders exactly like a declared
custom type: its alias and `Input` alias in the declared block, references at
input and plain positions, named zod/valibot schemas, the recursion check.
NewTypes that don't opt in stay inline everywhere. `TypeMapper.expand_plain/1`
maps a NewType's scalar members with their `scalar` entry's constraints
(`custom_fields?` is `custom_type?(definition)`), as its inline rendering does.

A type module the manifest reaches (a `manifest.types` definition, or an
`:unknown` node of `AshTypescript.Manifest.TypeUses.nodes/1`, which walks
`VerifyMappableTypes`' positions plus route inputs/returns and publication
returns) that still exports `typescript_type_name/0` or
`typescript_alias_name/0`, the names before the ash-rpc release, is a
`DslError` naming `typescript_type/0` / `typescript_type_alias/0`
(`CustomTypes.check_renamed_callbacks/1`, from `DecorateManifest` before
`check_alias_names/2`). A map-like `:unknown` type with the old callback and no
fields fails ash_rpc's undeclared-type check first.

`AshTypescript.Codegen.CustomTypeAliases` renders the block appended to the
type aliases (`// Declared custom types`, sorted by name): the plain alias
(`TypeMapper.expand_plain/1`, every key present) and, when
`TypeMapper.expand_input/1` differs, `<Name>Input` (`input_name/1`). Nested
aliased types reference their aliases (their input aliases inside an `Input`
alias). A definition whose fields reach a non-embedded resource
(`CustomTypeAliases.reaches_resource?/1`, through arrays, unions, typed
containers and named types; embedded resources end the walk) gets only its
plain alias: `input_name/1` and `SchemaCore.custom_type_schema_name/2` return
`nil`, so its input and schema uses stay inline (that resource has no
`InputSchema` and no zod/valibot schema). Before any alias or schema is
rendered, the orchestrator calls `CustomTypeAliases.check_recursive_types!/0`,
which throws "These aliased types contain themselves" for an aliased
definition reaching itself (resources end the walk): expanding it would not
terminate (`input_name/1` hung before this check). References:

| Position | Mapping |
|----------|---------|
| Inputs, calculation arguments, identity and `getBy` (`config_builder.ex`) | `map_type/3` `:input` → `input_name/1` (`map_plain_type(t, :input)` for identity/`getBy`) |
| Route results, channel payloads | `map_route_result_type/1` / `map_channel_payload_type/1` → `plain_name/1` |
| Filter values (`filter_types.ex`), action metadata (`metadata_types.ex`) | `map_plain_type(t, :output)`: typed containers plain, aliased types the alias, unions in schema form |
| Resource schemas, field selection, generic action results | inline `TypedMap` (unchanged) |

Known limitation: an embedded-resource field renders as its resource schema in
a plain alias and in filter values (`LineItem = {…, meta: TaskMetadataResourceSchema | null}`),
which requires the `__type` markers.

`AshTypescript.Manifest.Verifiers.VerifyCustomTypeNames` reports ("Types with
colliding TypeScript names found", one aggregated `DslError`
at `[:custom_types]`; Spark turns a verifier error into a compile warning, so it
fails `--warnings-as-errors`, and codegen re-runs it and fails) an alias shared
by two types,
an alias equal to another alias plus `Input` (every `<alias>Input` is reserved:
whether it is emitted needs rendering), a resource-derived name
(`X` + `ResourceSchema`, `AttributesOnlySchema`, `InputSchema`, `FilterInput`,
`FilterField`, `SortField`, embedded resources included), or one of the 43
fixed names (`reserved_names/0`: the 18 `TypeAliases.fixed_alias_names/0` plus
the 25 `export type`s scanned from `UtilityTypes.generate_utility_types/0`).
The orchestrator's codegen backstop throws for a duplicate `export type` in the
types file, a name a generated file (types, zod, valibot, RPC, routes,
channels; `validate_generated_names!/4`) imports from the types file and
declares locally, a name it imports from elsewhere (its own `import` lines:
phoenix `Channel`, zod `z`, valibot `v`, `import * as` modules) that it also
imports from the types file or declares (a schema `z` needs an empty
`zod_schema_suffix`), an alias equal to an `import_into_generated` /
`typed_controller_import_into_generated` `import_name`, and a schema name equal
to a `*_import_into_generated` one. Every fix hint is
`CustomTypes.rename_hint(:map)` (rename the alias: `ts_alias` or
`typescript_type_alias/0`); each verifier line ends in its type's hint, and
the closing line is "Rename one of them as each line says."

### Import Configuration

OTP app — it is read via `Application.get_env(:ash_typescript, :import_into_generated)`
in `codegen/shared_types_generator.ex` and `rpc/codegen/typescript_static.ex`):

```elixir
config :ash_typescript,

    %{import_name: "CustomTypes", file: "./customTypes"}
  ]
```

### Scalar Entries

For scalar **dependency types** you can't modify (e.g., `AshUUID.UUID`), declare a
`scalar` in the manifest module's `custom_types` section instead of the callback
(`config :ash_typescript, :type_mapping_overrides` is no longer read, and setting
it warns at manifest compile):

```elixir
custom_types do
  scalar AshUUID.UUID, :string                       # maps as its base type
  scalar MyDep.Code, :string, ts_type: "`code-${string}`"
  scalar MyDep.Path, :string, ts_type: {MyDep.Ts, :path, []}  # apply(m, f, [constraints | a])
end
```

`TypeMapper.unknown_module_mapping/2` takes the first that applies: the manifest
`scalar` entry's `ts_type`, `typescript_type/0`, the built-in `scalar`
entry's `ts_type` (only when the manifest has no `scalar` entry for the
module), then the base type of the manifest entry, else the built-in's. So a
manifest `scalar` with only `zod`/`valibot` keeps `typescript_type/0`. The
base type maps with the entry's constraints, or with the node's own when it is a
field of a declared custom type (`custom_fields?: true`).

**Decision rule**: Can you edit the type module? Use `typescript_type/0` callback. Can't edit it? Use a `scalar` entry.

### Unmappable Types (0.18)

A type the manifest generator classifies as `kind: :unknown` must be resolvable to a
TypeScript type or it is a **compile-time error**. Three layers:

1. **Accept-list** — `TypeMapper.unknown_module_mapping/2`
   (`lib/ash_typescript/codegen/type_mapper.ex`) is the single source of truth,
   shared by `map_type/3`, `TypeAliases`, and the verifier. Returns
   `{:ok, ts_type} | :unsupported`. Accepts: manifest `scalar` entries, custom
   types (`Introspection.is_custom_type?/1`, incl. manifest `type_name`
   decoration), and built-in `scalar` entries. It reads the entries from the
   configured manifest; the verifier wraps its walk in `with_manifest/2` so it
   reads the manifest being verified.

2. **Compile-time verifier** — `AshTypescript.Manifest.Verifiers.VerifyMappableTypes`
   walks every reachable type (resource fields, entrypoint action inputs/returns/
   metadata, `manifest.types` incl. embedded resources, recursing through arrays,
   unions, and typed-container fields) and raises **one aggregated**
   `Spark.Error.DslError` listing all offenders with locations:

   ```
   Unsupported types found — AshTypescript cannot map them to TypeScript:
   ```

   The same error has two more headings for custom types whose TypeScript
   comes from declared fields:
   `Undeclared map-like custom types found` (a map-like `:unknown` use,
   `AshRpc.Introspection.map_like_custom_type?/2`, with no fields; ash_rpc
   rejects wire uses first, so these are off the wire, e.g. an attribute of a
   resource whose only RPC action is generic), listed with the declaration
   hint; and `Map-like custom types that declare a TypeScript type` (a
   declared custom type definition, `AshRpc.Manifest.Custom.custom_type?/1`, or
   a map-like `:unknown` use, whose module exports `typescript_type/0` or
   has a `scalar` entry, the manifest's or a built-in), each with the
   migration message.

3. **Backstop raise** — `TypeMapper.raise_unsupported_type!/1` for paths that
   bypass the manifest:

   ```
   unsupported type <Module> — AshTypescript cannot map it to a TypeScript type.
   ```

**Carve-out**: module-less unknowns (`TypeResolver.resolve(nil)`, e.g. generic
actions with no return) still map to `any` — there is no module to point at.
Deliberate `any`s (`:term`, `Ash.Type.File`/`Function`, aggregate kinds) are untouched.

Custom types integrate at multiple levels:
- **Schema generation**: Type names used in resource schemas

## Common Issues

### Type System Issues
- **Type ambiguity**: Missing or incorrect `__type` metadata
- **Schema key mismatch**: Field doesn't exist in appropriate schema section
- **Calculation detection failures**: Resource vs primitive calculation misclassification

### Custom Type Issues
- **`Unsupported types found — AshTypescript cannot map them to TypeScript:`**: `VerifyMappableTypes` at manifest compile. Add `typescript_type/0` or a `custom_types` `scalar` entry for each listed module
- **`Undeclared map-like custom types found`** / **`returns an undeclared custom type`**: a `storage_type :map` or composite custom type with no declared fields. Declare them (a `map` entry, `typescript_fields/0`, or `composite?/1` + `composite_types/1`)
- **`Map-like custom types that declare a TypeScript type`**: remove `typescript_type/0` (or turn the `scalar` entry into a `map` one); the TypeScript is generated from the fields
- **`unsupported type <Module> — AshTypescript cannot map it to a TypeScript type.`**: same cause, hit via the `TypeMapper` backstop instead of the verifier
- **`Types with colliding TypeScript names found`**: `VerifyCustomTypeNames`. Set `ts_alias "…"` on one type's `map` entry, or `typescript_type_alias/0` on the type when no entry sets `ts_alias`
- **`Duplicate exported type names in …`** / **`… imports types from … that it also declares`** / **`… imports names that it also imports from … or declares`** / an alias or schema that is an `import_name`: the orchestrator backstop; the message names the custom type and how to rename its alias
- **Type not detected**: Ensure `typescript_type/0` callback implemented
- **Import not working**: Check `config :ash_typescript, import_into_generated:` (not your own OTP app)
- **TypeScript compilation fails**: Verify external type definitions exist and are accessible
- **Invalid field names in map constraints**: See [Field and Argument Name Mapping](./field-argument-name-mapping.md) for using `typescript_field_names/0` callback

## Unconstrained Map Handling

**Critical**: Actions that accept or return unconstrained maps (`:map` type without specific constraints) bypass standard type processing and field formatting systems.

### Input Map Behavior

> **Runtime:** keys pass through as-is.

### Output Map Behavior
When an action returns an unconstrained map:
- **No fields parameter**: The `fields` parameter is removed from generated function signature

> **Runtime:** the whole map comes back with its keys unchanged.

```typescript
// Generated function for unconstrained map output
function processData(params: {
  input: { rawData: Record<string, any> }  // Any map structure allowed
  // Note: no fields parameter
}): Promise<ProcessDataResult>;

// Result contains original field names from Elixir
type ProcessDataResult = {
  success: true;
  data: Record<string, any>;  // Entire map returned as-is
} | {
  success: false;
  errors: ErrorInfo[];
};
```

### Type Generation Implications
- **Schema Generation**: Unconstrained maps generate `Record<string, any>` (the default of `AshTypescript.untyped_map_type/0` — configurable via `config :ash_typescript, untyped_map_type:`)

### Testing Considerations
When testing actions with unconstrained maps:
1. **Input Testing**: Test with various arbitrary map structures
2. **Output Testing**: Verify entire map is returned without field selection
3. **Field Name Preservation**: Ensure snake_case/camelCase formatting is preserved
4. **Type Compilation**: Verify TypeScript compiles with `any` types
